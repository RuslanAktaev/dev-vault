# HTTP-кеширование

**Определение.** Кеш хранит копии ответов, чтобы не ходить за ними на сервер каждый раз. Кеши стоят в нескольких местах на пути ответа (браузер, CDN, прокси), и каждый может отдать устаревшее. Управляют ими заголовок `Cache-Control` и связанные с ним `ETag` и `Vary`.

## Директивы Cache-Control

| Директива | Смысл |
|---|---|
| `max-age=N` | Сколько секунд копия считается свежей. Действует для всех кешей |
| `s-maxage=N` | То же, но только для общих кешей (CDN, прокси). Для них перекрывает `max-age`, браузер её игнорирует |
| `no-cache` | Хранить можно, но перед каждым использованием сверяться с сервером |
| `no-store` | Не сохранять нигде (для чувствительных данных) |
| `private` | Ответ для одного человека: хранить может только браузер, CDN и прокси — нет |
| `public` | Ответ одинаков для всех: можно хранить и в личном, и в общем кеше |
| `immutable` | Содержимое никогда не изменится |
| `stale-while-revalidate=N` | После срока отдать устаревшую копию и обновить её в фоне |

**`no-cache`, `no-store` и `immutable`.**
- `no-store` — не сохранять нигде, ни в браузере, ни в CDN. Каждый запрос получает полный ответ.
- `no-cache` — копию хранить можно, но перед каждым использованием её сверяют с сервером через [[ETag]]. Название обманчиво: кеш есть, просто его каждый раз проверяют.
- `immutable` — противоположность `no-store`. До конца `max-age` копия считается неизменной, и браузер не сверяет её даже при обновлении страницы. Ставится вместе со сроком (`public, max-age=31536000, immutable`) на файлы с хешем в имени. Браузер, который не знает `immutable`, игнорирует директиву и работает по `max-age`.

**Сверка (revalidation).** Сервер отдаёт `ETag`, а браузер в следующий раз шлёт `If-None-Match: <etag>`. Если ничего не изменилось, приходит `304` без тела. Аналог по времени: `Last-Modified` + `If-Modified-Since`. Подробно в [[ETag]].

## Личный и общий кеш
`Cache-Control` — инструкция всем, кто по пути может сохранить копию ответа. Сам он никакой кеш не настраивает. Кеши отличаются тем, кого обслуживают:

```
Твой сервер  →  CDN  →  браузер пользователя
               (общий)   (личный)
```

| Кеш | Тип | Нужно ли настраивать |
|---|---|---|
| Браузер | Личный: один пользователь | Нет, он следует твоим заголовкам |
| Service Worker | Личный, управляется кодом страницы | Код пишешь сам |
| CDN | Общий: копию получит любой следующий | Подключить и проверить его правила |
| Reverse proxy (nginx, Varnish) | Общий | Включить самому (`proxy_cache` в nginx), дальше он читает заголовки |
| Redis, память процесса | Кеш твоего кода, общий для всех запросов | Всё сам, заголовков не читает → [[Redis-кеш]] |

Пример: `Cache-Control: public, max-age=60, s-maxage=3600` — браузер хранит копию минуту, CDN — час.

**Личный кеш и личный ответ — разные вещи.** Кеш бывает личным или общим: это про то, где лежит копия. Ответ бывает личным или публичным: это про то, чьи в нём данные. `private` согласует одно с другим: «ответ личный, клади только в личный кеш».

| Ответ | Куда положили | Итог |
|---|---|---|
| Публичный | Любой кеш | Нормально |
| Личный | Браузер | Нормально |
| Личный | CDN без защиты | Утечка: следующий пользователь получит чужие данные |

Общий кеш общий по природе места: CDN остаётся общим, даже если в нём лежит защищённое содержимое. Как отдавать личные файлы через CDN, разобрано в [[Подписанные ссылки]].

## Что меняют public и private
Без `private` и `public` кеш работает по стандартным правилам: хранит `GET` с кешируемым статусом (`200`, `301`, `404` и ряд других), а общий кеш не использует ответ на запрос с `Authorization`. `public` снимает часть запретов, `private` полностью запрещает хранение общим кешам.

| Ситуация | Без заголовка | `public` | `private` |
|---|---|---|---|
| Браузер (личный кеш) | хранит | хранит | хранит |
| CDN, обычный `GET` `200` с `max-age` | хранит | хранит (разницы нет) | не хранит |
| CDN, запрос с `Authorization` | не хранит | хранит | не хранит |

Ограничения:
- `public` не задаёт срок (его задают `max-age` и `s-maxage`) и не отменяет ни `no-store`, ни правила самого CDN. Например, у Cloudflare по умолчанию HTML и JSON не кешируются.
- `private` — инструкция для кешей, а не защита данных: копия всё равно лежит на диске браузера. Для чувствительного нужен `no-store`.
- Если сомневаешься, ставь `private`. Ошибка в эту сторону стоит потери кеша на CDN, а в обратную — утечки.

| Заголовок | Браузер | CDN |
|---|---|---|
| `private, max-age=60` | 60 с | не хранит |
| `public, max-age=60` | 60 с | 60 с |
| `private, no-cache` | хранит и сверяет | не хранит |
| `public, max-age=0, s-maxage=3600` | сверяет каждый раз | час |
| `no-store` | не хранит | не хранит |

## Cache-Control — просьба, а не принуждение
Заголовок только сообщает кешу, что можно хранить. Выполнит ли кеш просьбу, решают он сам и его настройки.
- **Правило сильнее заголовка.** Ответ с данными пользователя ушёл без `private`, а на CDN включено правило «кешировать всё в `/api/*`». CDN сохранит ответ, и следующий пользователь получит чужие данные. Поэтому `private` ставят на всё персональное, а настройки CDN проверяют отдельно.
- **Часть ответов не кешируют и без запрета.** Общий кеш не сохраняет ответ на запрос с `Authorization`. Многие CDN не кешируют ответы с `Set-Cookie` (это зависит от настроек).

## Хеш в имени файла
Хеш — короткая строка, вычисленная от содержимого файла. Тот же файл даёт тот же хеш, изменился хоть байт — хеш другой. Сборщики (Vite, Webpack, Next.js) вставляют его в имя: `app.js` → `app.3f9a1c.js`.
- По такому имени содержимое никогда не меняется, поэтому файл кешируют на год: `max-age=31536000, immutable`.
- Вышла новая версия: HTML ссылается на файл с новым именем, браузер качает его, а старый остаётся в кеше невостребованным.
- Без хеша пришлось бы выбирать между частыми загрузками и устаревшим `app.js` после обновления.

**Деплой.** Политика для файлов с хешем фиксирована, меняется только имя. О новых именах браузер узнаёт только из HTML, поэтому HTML надолго не кешируют (`no-cache` с ETag или очень короткий `max-age`). Старые файлы после деплоя стоит какое-то время держать на сервере: у пользователя может быть открыта вкладка со старым HTML, который ссылается на старые имена. В Next.js без этого бывают ошибки загрузки чанков после деплоя.

## Стандартная схема
- JS и CSS с хешем в имени: `max-age=31536000, immutable`.
- HTML: `no-cache`, чтобы он всегда ссылался на актуальные файлы.
- API с данными пользователя: `private` или `no-store`.

## Vary
Если ответ зависит от заголовка запроса (`Accept-Encoding`, `Origin`, `Accept-Language`), этот заголовок нужно перечислить в `Vary`. Иначе общий кеш отдаст одному пользователю ответ, предназначенный другому.

## Как проверить, что кеш работает
Поставленный заголовок ещё не значит, что его кто-то исполнил. В Network смотри:
- `Age: 120` — ответ пролежал в кеше 120 секунд. Это стандартный заголовок, и кеши вычитают его из срока свежести: при `max-age=300` и `Age: 120` копия свежа ещё 180 секунд;
- `X-Cache: HIT`, `cf-cache-status: HIT`, `x-vercel-cache` — пометки CDN. Они только показывают результат и на поведение не влияют;
- `200 (from disk cache)` — ответ из личного кеша браузера.

Схему ломают `fetch(..., { cache: 'no-store' })` и галка «Disable cache» в DevTools.

## Частые ошибки понимания
- **«`no-cache` = не кешировать».** Нет, это «хранить, но каждый раз сверять». Не кешировать — это `no-store`.
- **«`private` защищает данные».** Нет. Это только запрет общим кешам, копия всё равно лежит на диске браузера.
- **«Поставил `public, max-age` — CDN закеширует».** Правила CDN могут это перекрыть. Cloudflare HTML и JSON без правила не кеширует.
- **«Заголовок стоит — значит работает».** Проверяй по `Age` и `HIT`.
- **Личный кеш и личный ответ — не одно и то же.** Первое — где лежит копия, второе — чьи в ней данные.
- **Кешировать HTML надолго.** Тогда после деплоя браузер продолжит ссылаться на старые чанки.
