# CDN

**Определение.** CDN (Content Delivery Network, сеть доставки контента) — сеть серверов по всему миру, которая стоит перед твоим сервером. Через неё идёт весь трафик подключённого домена. Что с этим трафиком делать (кешировать, защищать, ускорять), задаётся настройками. CDN нужен не только для статики.

## Участвует и кеширует — разные вещи
Если имя (хост) подключено к CDN (в DNS оно указывает на CDN; у Cloudflare это называется «проксирование»), через CDN идёт **любой** запрос к этому имени: HTML, API, картинки. CDN может сохранить копию и отдавать её сам. А может просто передать запрос на твой сервер, но и тогда снимет TLS, отфильтрует ботов и сожмёт ответ.

| Что делает CDN | Статика | Динамика (HTML, API) |
|---|---|---|
| Кеширует и отдаёт с ближайшего узла | По умолчанию | Если настроить (`s-maxage`, правила в панели) |
| Снимает TLS | Да | Да |
| Держит постоянные соединения до твоего сервера | Да | Да |
| Сжимает ответы (gzip, br) | Да | Да |
| Защищает: WAF, DDoS, боты, rate limiting | Да | Да. Часто это главная причина ставить CDN перед API |
| Edge-функции (Workers, Vercel Edge) | Нет | Код выполняется на узле, и ответ может собраться, не доходя до сервера |

## Что лежит в кеше CDN
- Как правило, ответ целиком: статус, заголовки, тело. JSON кешируется так же, как HTML или картинка, `Content-Type` для CDN просто заголовок.
- Большие файлы хранятся кусками, и на запрос части файла (`Range`) CDN отдаёт нужный кусок.
- **Ключ копии**: метод (кешируются GET и HEAD), полный URL вместе с query-строкой и значения заголовков из `Vary`.
- По умолчанию многие CDN не сохраняют ответы на POST, ответы 5xx и ответы с `Set-Cookie`.

```
GET /api/products?category=books   → 200 JSON, сохранён под этим URL
GET /api/products?category=books   → из кеша CDN
GET /api/products?category=toys    → другой ключ, запрос идёт на сервер
```

**Включено ли кеширование по умолчанию**, зависит от CDN. Cloudflare сам кеширует по расширению файла (`.js`, `.css`, картинки), а HTML и JSON — только по правилу в панели, даже при `public, max-age`. Правило в панели может перекрыть заголовок. Браузер при этом всегда следует заголовкам. Проверка: `Age`, `X-Cache: HIT`, `cf-cache-status: HIT` в ответе.

## Какие запросы проходят через CDN
CDN привязан к **имени хоста** в адресе, а не к виду запроса.
- Родительский домен роли не играет: `example.com` и `api.example.com` — два разных имени, и каждое подключают к CDN отдельно.
- Не важно, кто делает запрос (браузер или сервер) и что стоит за адресом (Laravel, Django, Node).
- Адрес в запросе из серверного кода задаёшь ты сам, например через `API_URL`. Он может быть внутренним (`http://backend:8000`, если Next.js и бэкенд в одной сети) или публичным (`https://api.example.com`, если они развёрнуты отдельно).

| Кто делает запрос | Адрес | CDN на пути? |
|---|---|---|
| Браузер | Имя подключено к CDN (`example.com/api/...`, `api.example.com`) | Да |
| Браузер | Имя не подключено, указывает прямо на сервер | Нет |
| Сервер Next.js (серверный компонент, route handler, server action) | Публичный адрес с подключённым именем | Да: для CDN сервер Next.js — обычный клиент |
| Сервер Next.js | Внутренний адрес (`http://backend:8000`) | Нет: запрос не выходит из внутренней сети |
| Любой сервер | Чужой API | Твоего CDN нет, у самого сервиса может быть свой |

- **Внутренний адрес** — на пути нет HTTP-кешей, и `Cache-Control` ничего не меняет, пока клиент не кеширует сам. У Next.js есть свой кеш серверного `fetch`, но им управляют параметры вызова (`cache`, `revalidate`, `use cache`), а не заголовки ответа бэкенда.
- **Запрос из браузера**, особенно GET, проходит через браузерный кеш и через CDN (если имя подключено), и заголовки работают. POST, PUT, DELETE не кешируются.
- **CORS** нужен только запросу из браузера на другое имя. Серверный запрос (серверный компонент, route handler, server action, любой бэкенд) CORS не проверяет.

## Что ставить по типам ответов

| Что отдаёшь | Типичные заголовки | Что делает CDN |
|---|---|---|
| Статика с хешем (`app.3f9a1c.js`) | `max-age=31536000, immutable` | Кеширует сам |
| HTML (общий случай) | `no-cache` | Обычно проксирует |
| Публичный HTML (блог, каталог) | `s-maxage=60, stale-while-revalidate=...` | Кеширует намеренно, разгружает сервер |
| Публичный API (каталог, курсы валют) | `public, s-maxage=60` | Кеширует: сервер получает один запрос в минуту вместо тысяч |
| API с данными пользователя | `private` или `no-store` | Не должен кешировать |

## Пример на Next.js
Next.js сам выставляет `Cache-Control` в зависимости от типа страницы (App Router, документация v16). Исполняет эти заголовки то, что стоит перед ним.

| Страница | Что выставляет Next.js |
|---|---|
| Статическая (нет `cookies()`, `headers()`, `searchParams`) | Кеш на год |
| С `export const revalidate = 60` (ISR) | `s-maxage=60` + `stale-while-revalidate` |
| Динамическая (читает куки пользователя) | `private, no-cache, no-store, max-age=0, must-revalidate` |

Проверять надо на сборке, в `next dev` заголовки другие:

```bash
npm run build && npm start
curl -sI http://localhost:3000/about | grep -i cache-control
```

`Cache-Control`, выставленный вручную (`headers()` в `next.config` или в route handler), Next не перезаписывает:

```js
// next.config.mjs
export default {
  async headers() {
    return [{
      source: '/about',
      headers: [{ key: 'Cache-Control', value: 'public, s-maxage=3600' }],
    }];
  },
};
```

**Где вступает CDN.**
- **Vercel** читает заголовки автоматически: статика и ISR кешируются на CDN, динамика нет.
- **Свой сервер за Cloudflare**: `_next/static` с хешем кешируется по расширению, HTML (`/about`, `/blog/*`) — только по правилу в панели. `private` и `no-store` с динамических страниц Cloudflare уважает.

## Как обновить копию в CDN

| Способ | Как работает | Когда |
|---|---|---|
| Дождаться срока | Копия устареет сама по `s-maxage` | Минуты устаревших данных допустимы |
| Purge | Удалить копию через панель или API: по URL, префиксу, метке (`Cache-Tag`, `Surrogate-Key`) или всё сразу | Контент изменился, ждать нельзя. Вызывают из CI после деплоя или вебхуком CMS |
| Новый URL | Хеш в имени или версия в пути: для CDN это другой ресурс | Статика, purge не нужен |
| Короткий срок и `ETag` | CDN чаще сверяется с сервером и при `304` не качает тело | Данные меняются часто, мгновенная свежесть не нужна |
| `stale-while-revalidate` | После срока CDN сразу отдаёт старую копию и обновляет её в фоне | Важна скорость, один запоздавший ответ допустим. Поддержка зависит от CDN |
| Инвалидация во фреймворке | `revalidatePath`, `revalidateTag` в Next.js | CDN встроен в хостинг |

**Purge очищает только CDN.** Копии в браузерах остаются до конца своего `max-age`. Поэтому для страниц, которые должны обновляться, сроки двух кешей задают раздельно: `Cache-Control: public, max-age=0, s-maxage=3600`. Браузер каждый раз сверяет копию с CDN, а CDN держит её час и сбрасывается purge-ем при изменении контента.

Purge доходит до узлов за время от секунд до минут. Лимиты и стоимость зависят от CDN. После очистки популярной страницы на сервер может хлынуть лавина запросов, но хорошие CDN склеивают такие запросы в один.

## Подводные камни
- **Query-строка входит в ключ.** Лишние параметры (`?_=timestamp`, `utm_...`) создают отдельные копии одного и того же ответа.
- **`Authorization`.** Общий кеш по умолчанию не сохраняет такие ответы, если это явно не разрешено.
- **`Set-Cookie`.** Многие CDN такие ответы не кешируют, но это зависит от настроек.
- **`Vary`.** Если ответ зависит от заголовка (`Accept-Language`), его нужно указать. Иначе одному пользователю отдадут ответ для другого.
- **Устаревшие данные.** Пока копия свежая, CDN отдаёт старое. Варианты обновления — в таблице выше.

## Частые ошибки понимания
- **«CDN — это только для статики».** Через подключённое имя идёт весь трафик. Кешировать динамику — отдельная настройка, а защита и TLS работают всегда.
- **«Подключил CDN — всё кешируется».** Cloudflare HTML и JSON без правила не кеширует.
- **«Purge обновил страницу у всех».** Браузерные копии живут до конца своего `max-age`.
- **«Серверный fetch из Next.js тоже идёт через CDN».** Только если адрес публичный, а имя подключено. По внутреннему адресу CDN нет.
- **«Мой домен на CDN — значит и поддомены».** Каждое имя подключают отдельно.
