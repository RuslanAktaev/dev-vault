# Сессии и JWT

**Ключевая идея.** HTTP ничего не помнит, поэтому после логина нужно доказывать, кто ты, в каждом запросе. Есть два способа:
- **серверная сессия**: клиент носит случайный ключ, данные лежат на сервере;
- **JWT**: клиент носит сами данные, подписанные сервером.

Для обычного веб-приложения «браузер ↔ свой бэкенд» серверная сессия в HttpOnly-куке проще и надёжнее. JWT оправдан, когда токен проверяют разные сервисы без общей БД.

| | Серверная сессия | JWT |
|---|---|---|
| Что хранится | В куке случайный `session_id`, данные в Redis или БД | В токене подписанные данные (`sub`, `exp`, роли) |
| Как проверяется | Запросом в хранилище | Проверкой подписи, без БД |
| Отзыв | Мгновенный: удалить запись | До `exp` невозможен без чёрного списка |
| Цена | Нужно общее хранилище | Отзыв и ротация сложнее |
| Где оправдан | Классический веб | Много сервисов, мобильные клиенты, внешние API, OAuth/OIDC |

## Серверная сессия

| Термин | Что это |
|---|---|
| Сессия | Запись о пользователе на сервере: `{ userId: 42, role: 'admin' }` |
| Session id | Случайная строка, ключ к записи. О пользователе ничего не говорит |
| Хранилище | Где лежат записи: Redis, БД, файлы, память процесса |
| Кука | Контейнер, в котором ездит session id. Для браузера это обычная кука |
| `sid` | Не термин, а имя куки (`sid`, `connect.sid`, `PHPSESSID`) |

**Логин:**
1. Сервер проверяет пароль.
2. Создаёт session id криптостойким генератором.
3. Записывает в хранилище `id → { userId }` со сроком жизни.
4. Отвечает `Set-Cookie`.

**Каждый следующий запрос:**
1. Браузер сам прикладывает куку.
2. Сервер ищет запись по id.
3. Нашёл — пользователь известен. Не нашёл — `401`.

**Кто что делает.** Redis хранит записи и сам удаляет их по TTL. Остальное делает фреймворк или библиотека (`express-session`, Laravel, `Plug.Session`, Auth.js): создаёт id, ставит куку, ищет запись, продлевает срок. Руками сессии почти не пишут. От разработчика обычно нужно:
- выбрать хранилище (в Laravel `SESSION_DRIVER=redis`);
- класть данные в сессию;
- менять id при логине (`$request->session()->regenerate()`), чтобы закрыть session fixation.

**Конец сессии.** Сервер не знает, что вкладку закрыли. Сессия заканчивается по таймауту простоя, по абсолютному сроку, при выходе или принудительно (смена пароля, бан). Кука без срока пропадает при закрытии браузера, но запись на сервере живёт до своего срока.

**Нюансы.**
- На каждое устройство и браузер своя сессия, вкладки одного браузера делят одну.
- Кука для session id не обязательна: его можно возить и в `Authorization: Bearer`.
- API-токен Laravel Sanctum устроен так же (запись в БД, ключ в заголовке), но выдаётся явно и живёт долго. Для SPA Sanctum использует обычные сессии с кукой.
- Session id должен быть случайным (не меньше 128 бит), секретным (`HttpOnly`, `Secure`) и новым при каждом логине.

## JWT

### Из чего состоит
Одна строка из трёх частей через точку: `header.payload.signature`.

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInJvbGUiOiJ1c2VyIn0.3f9a1c...
└───── header ──────┘ └────────── payload ─────────────┘ └ signature ┘
```

| Часть | Что внутри | После раскодирования |
|---|---|---|
| `header` | Как подписан токен | `{"alg": "HS256", "typ": "JWT"}` |
| `payload` | Данные (claims) | `{"sub": "42", "role": "user", "exp": 1790000000}` |
| `signature` | Подпись от header и payload | Байты, не JSON |

**Header и payload** — это JSON в base64url. Это кодирование, а не шифрование: раскодировать может кто угодно и без ключа.

```js
const [header, payload, signature] = token.split('.');
JSON.parse(Buffer.from(payload, 'base64url').toString()); // { sub: '42', role: 'user', exp: ... }
```

**Signature** считается от строки `header.payload`. При HS256 это HMAC с общим секретом, при RS256 — подпись приватным ключом.

### Как сервер проверяет токен
Сервер берёт `header` и `payload` из присланной строки, сам считает подпись тем же способом и сравнивает с присланной. Если подписи совпали, токен не меняли. Стоит изменить хоть байт в payload (например, `role: admin`), и подпись не сойдётся. Итог: **подделать токен без ключа нельзя, а прочитать можно.** Подпись защищает от подмены, а не от чтения.

### Что из этого следует
- Данные о пользователе лежат в самом токене, сервер ничего не хранит. Проверка — это проверка подписи, без БД.
- Поэтому отозвать токен до `exp` нельзя без дополнительного хранилища (чёрного списка).
- Payload видит клиент, поэтому класть в него можно только несекретное: id, роль, срок.
- Стандартные claims: `sub` (кто), `exp` (до когда), `iat` (когда выдан), `iss` (кто выдал), `aud` (для кого).
- Проверять нужно `exp`, `iss`, `aud` и фиксировать допустимый алгоритм. Известные грабли:
  - сервер принимает `alg: none`;
  - алгоритм подменяют с RS256 на HS256, и публичный ключ используется как общий секрет.
- Алгоритмы: HS256 (общий секрет) или асимметричные RS256/ES256/EdDSA. Для асимметричных публичный ключ раздаётся через JWKS.
- Access-токен делают коротким (5–15 минут). Долгоживущий refresh-токен хранят отдельно и ротируют при каждом использовании, отслеживая повторное использование старого.

### Где хранить токен на фронте

| Место | Плюс | Минус |
|---|---|---|
| `localStorage` | Просто | Любой XSS украдёт токен |
| HttpOnly-кука | XSS не может её прочитать | Нужна защита от CSRF |
| BFF (токены на сервере, в браузере кука сессии) | Токены не доходят до JS | Нужен свой серверный слой |

## Частые ошибки понимания
- **«JWT зашифрован».** Нет, только подписан. Секретов в payload быть не должно.
- **«JWT всегда лучше сессий».** Для браузера со своим бэкендом сессия проще: мгновенный отзыв, нет проблем с ротацией.
- **«Закрыл вкладку — сессия кончилась».** Сервер об этом не знает. Запись живёт до таймаута.
- **Не менять session id при логине.** Это открывает session fixation.
- **Session id или кука, `sid` или сессия.** `sid` — имя куки. Кука только возит id, а сессия — запись на сервере.
- **Проверять только подпись.** Нужны ещё `exp`, `iss`, `aud` и фиксированный алгоритм.

## Связи
- [[Cookies]] — session id ездит в HttpOnly-куке. Срок жизни куки и серверной сессии не зависят друг от друга.
- [[OAuth 2.0]] — `access_token` и `refresh_token` часто JWT. BFF держит токены на сервере, браузеру отдаёт куку сессии.
- [[OIDC]] — `id_token` — это JWT, его проверяют теми же правилами. После входа обычно создают свою серверную сессию.
- [[Отладка веб-запросов]] — симптомы «401/403» и «JWT invalid».
