# HTTPS за прокси

**Определение.** Обычно TLS снимает reverse proxy (nginx, балансировщик, CDN), а до приложения запрос идёт по обычному HTTP. Приложение видит только этот внутренний участок и не знает, что снаружи был HTTPS. Заголовки `X-Forwarded-*` передают ему, каким запрос был до прокси.

## Схема: TLS termination
```
браузер ──HTTPS──► reverse proxy ──HTTP──► приложение
        ◄──HTTPS──               ◄──HTTP──
```
Ответ идёт обратным путём: прокси шифрует его для браузера.

| Вариант | Как | Что видит приложение |
|---|---|---|
| TLS termination | Прокси снимает TLS, дальше HTTP | `http`, IP прокси. Нужны `X-Forwarded-*` |
| TLS passthrough | Прокси пересылает TCP по SNI, не расшифровывая | Сам HTTPS, сертификат на приложении. Прокси не видит HTTP и не может добавить заголовки |
| Re-encryption | Прокси снимает TLS и открывает новое TLS-соединение до приложения | `https`, но IP и хост клиента всё равно только из заголовков |
| Cloudflare Flexible | Браузер → Cloudflare по HTTPS, Cloudflare → origin по HTTP | `http`. Если origin сам редиректит на https — бесконечный редирект |

## Что ломается, если приложение не знает про HTTPS
- **Бесконечный редирект.** Приложение редиректит «http → https», браузер приходит по https, прокси снова шлёт в приложение по http, и всё повторяется. Редирект делает приложение, а не прокси.
- **Ссылки и `Location` с `http://`**: абсолютные URL, редиректы после логина, ссылки в письмах.
- **Mixed content**: страница по https подключает ресурсы по сгенерированным `http://` URL, браузер их блокирует.
- **Secure-куки не ставятся**: фреймворк считает соединение небезопасным и не отдаёт куку с `Secure` (например, `express-session` с `cookie.secure: true`). Браузер тут ни при чём, он видит https.
- **OAuth `redirect_uri`** собирается как `http://...` и не совпадает с зарегистрированным → `redirect_uri mismatch`.
- **IP клиента** — у всех запросов IP прокси: ломаются rate limiting, логи, гео.

## Заголовки
| Заголовок | Что передаёт | Пример |
|---|---|---|
| `X-Forwarded-Proto` | Исходную схему | `https` |
| `X-Forwarded-For` | Цепочку IP: клиент, затем каждый прокси дописывает адрес того, от кого получил запрос | `203.0.113.7, 10.0.0.2` |
| `X-Forwarded-Host` | Исходный `Host` | `example.com` |
| `Forwarded` (RFC 7239) | Стандартная замена трёх `X-Forwarded-*` | `Forwarded: for=203.0.113.7;proto=https;host=example.com` |

`X-Forwarded-*` — де-факто стандарт, `Forwarded` — официальный, но поддерживается реже.

## Безопасность
- Клиент может прислать любые `X-Forwarded-*` сам. Доверять им можно **только от своих прокси**.
- По умолчанию фреймворки заголовки игнорируют. Доверие включают явно: `trust proxy`, `TrustProxies`.
- **`X-Forwarded-For` читают справа налево**: правые адреса дописаны своими прокси, их отбрасывают, и первый недоверенный адрес — клиент. Самый левый адрес мог подставить клиент.
- Доверять всем (`*`, `true`) безопасно, только если приложение недоступно напрямую, мимо прокси.
- Свой внешний прокси должен **перезаписывать** `X-Forwarded-Proto` и `X-Forwarded-Host`, а не передавать клиентские.

## Настройка
**Nginx** — передать заголовки:
```nginx
location / {
  proxy_pass http://app:3000;
  proxy_set_header Host              $host;
  proxy_set_header X-Forwarded-Proto $scheme;
  proxy_set_header X-Forwarded-Host  $host;
  proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for; # дописывает $remote_addr к пришедшему
}
```
Если сам nginx стоит за другим прокси (CDN, балансировщик), `$scheme` будет `http`: схему надо брать из заголовка внешнего прокси.

**Express** — включить доверие, тогда `req.protocol`, `req.secure`, `req.ip`, `req.hostname` учитывают заголовки:
```ts
app.set('trust proxy', 1); // доверять одному хопу; можно 'loopback' или список IP/подсетей
```

**Laravel** — middleware `TrustProxies`:
```php
// Laravel 11+: bootstrap/app.php
->withMiddleware(function (Middleware $middleware) {
    $middleware->trustProxies(at: ['10.0.0.0/8']); // или '*', если приложение недоступно напрямую
})
```
В Laravel 10 и раньше — свойство `$proxies` в `App\Http\Middleware\TrustProxies`.

**Next.js self-hosted** (`next start` за nginx):
- Флага `trust proxy` нет. Nginx передаёт заголовки, в коде их читают сами: `(await headers()).get('x-forwarded-proto')`.
- Auth.js за прокси: `AUTH_TRUST_HOST=true` (доверять `X-Forwarded-Host`) или явный `AUTH_URL`.
- Абсолютные URL надёжнее строить из конфига (публичный URL сайта), а не из заголовков запроса.

## Редирект http → https — на прокси
Прокси знает, по какой схеме пришёл запрос, приложение — нет. Поэтому редирект делают на прокси:
```nginx
server {
  listen 80;
  server_name example.com;
  return 301 https://$host$request_uri;
}
```
Приложение при этом редирект не делает или делает только при включённом доверии к прокси.

## Не путать
- **[[HSTS]]** — браузер сам идёт по https, не делая запрос по http. Приложению, которое не знает про https, это не помогает. Если приложение ставит HSTS только при `req.secure`, за прокси без доверия заголовок не уйдёт вовсе.
- **CSP `upgrade-insecure-requests`** ([[XSS и CSP]]) — браузер переписывает `http://` ресурсы страницы на `https://`. Маскирует mixed content, но не чинит `Location`, куки и `redirect_uri`.

## Reverse proxy и forward proxy
| | Reverse proxy | Forward proxy |
|---|---|---|
| Стоит | Перед сервером | Перед клиентом |
| Настраивает | Владелец сайта | Клиент или его сеть (корпоративный прокси) |
| Клиент знает о нём | Нет, видит только домен | Да, прокси прописан в настройках |
| Примеры | nginx, балансировщик, CDN | HTTP/HTTPS-прокси, корпоративный шлюз |

Для HTTPS forward proxy получает `CONNECT example.com:443` и просто туннелирует TCP: содержимого он не видит, только хост. Исключение — корпоративные прокси с расшифровкой, которые ставят свой корневой сертификат ([[HTTPS и TLS]]).

## Диагностика
```bash
curl -I http://example.com   # ждём 301, Location: https://..., Server: nginx (редирект делает прокси)
curl -I https://example.com  # ждём 200. Если снова 301 на https — приложение не знает про https
curl -IL --max-redirs 5 https://example.com  # увидеть цепочку редиректов
```
- **`Location`** — куда редиректят. `http://` в ответе на https-запрос — приложение собрало URL по своей схеме.
- **`Server`** (и `X-Powered-By`) — кто ответил: прокси или приложение.

## Частые ошибки понимания
- **«Сайт по HTTPS — значит, приложение знает про HTTPS».** За TLS termination приложение видит HTTP.
- **«Редирект на https надо делать в приложении».** Это и даёт бесконечный редирект. Его место — прокси.
- **«Клиентский IP — самый левый в `X-Forwarded-For`».** Его может подделать клиент. Читать справа, отбрасывая свои прокси.
- **«Достаточно, чтобы nginx передал заголовки».** Приложение их проигнорирует, пока не включён `trust proxy` / `TrustProxies`.
- **«HSTS или `upgrade-insecure-requests` решают проблему».** Это браузерные механизмы, они не меняют того, что видит приложение.
