# Идемпотентность и чистые функции

## Термины

| Термин | Вопрос, на который отвечает | Да | Нет |
|---|---|---|---|
| **Детерминированность** | Дают ли одинаковые аргументы всегда одинаковый результат? | `abs(-5)` | `Date.now()`, `Math.random()`, функция, читающая меняющуюся внешнюю переменную |
| **Побочный эффект** | Меняет ли функция что-то снаружи себя? | `arr.push(1)`, запись в БД, `fetch` с POST | `abs(x)` |
| **Чистая функция** | Детерминирована и без побочных эффектов? | `(a, b) => a + b` | `x => x * (1 + tax)` (читает внешнее) |
| **Идемпотентность** | Даёт ли повтор что-то сверх первого раза? | `abs`, `trim`, `PUT` | `addOne`, `counter++`, `POST` |
| **Safe** (HTTP) | Не меняет ли запрос по своему назначению состояние сервера? | `GET`, `HEAD`, `OPTIONS` | `POST`, `PUT`, `DELETE`, `PATCH` |
| **Cacheable** (HTTP) | Можно ли сохранить ответ и отдать его повторно? | `GET`, `HEAD` | `PUT`, `DELETE`, на практике `POST` |

Детерминированность, отсутствие побочных эффектов и идемпотентность друг от друга не зависят. Из них составлена чистота. Safe и cacheable относятся к HTTP-запросам, а не к функциям.

**Что сравнивают.** Детерминированность сравнивает два независимых вызова с одинаковыми аргументами и смотрит на **возвращаемое значение** («что вернётся»). Идемпотентность сравнивает один вызов с несколькими подряд и смотрит на **итог**, то есть на значение или состояние («что изменится»).

## Чистая функция

Чистая функция — это детерминированность плюс отсутствие побочных эффектов. Результат зависит только от аргументов. Снаружи функция ничего не меняет и не читает ничего изменяемого.

```js
const add = (a, b) => a + b;                 // чистая
const price = (x) => x * (1 + tax);          // нет: читает внешнюю изменяемую tax
const addItem = (i) => cart.push(i);         // нет: меняет внешний cart
const id = () => Date.now() + Math.random(); // нет: время и случайность
```

### Константы снаружи
Нарушает чистоту не само обращение к внешнему, а чтение того, что **может измениться**.

```js
const TAX = 0.12;
const price1 = (x) => x * (1 + TAX);         // чистая: TAX не может измениться

let tax = 0.12;
const price2 = (x) => x * (1 + tax);         // нечистая: tax переприсвоят, и тот же x даст другой результат

const config = { tax: 0.12 };
const price3 = (x) => x * (1 + config.tax);  // нечистая: const защищает только привязку, а config.tax можно поменять
```

### Почему `fetch` делает функцию нечистой
`fetch` — это ввод-вывод, и он ломает оба условия чистоты.
- **Детерминированность**: ответ зависит от внешнего мира (данные на сервере, сеть, время). Один и тот же URL возвращает разное.
- **Побочные эффекты**: отправка запроса уже действие во внешнем мире, а POST/PUT/DELETE ещё и меняют сервер.

Значит, любая функция, внутри которой есть `fetch`, нечистая, даже если она только читает через GET.

**Где нужна чистота:** в тестах, мемоизации, редьюсерах, рендере React. Сетевые вызовы выносят в эффекты и обработчики.

## Два смысла идемпотентности

| | Функции (математика, ФП) | Операции и запросы (HTTP, БД, API) |
|---|---|---|
| Что проверяют | `f(f(x)) = f(x)`: функцию применяют к её же результату | Повтор **того же** вызова оставляет то же состояние, что и один вызов |
| Идемпотентны | `abs`, `floor`, `trim`, `toLowerCase` | `PUT`, `DELETE`, `UPDATE … SET city = 'Astana'`, `mkdir -p` |
| Не идемпотентны | `addOne`, `sqrt` | `POST`, `INSERT`, `counter++`, `echo x >> file` |

```js
// функции: f(f(x)) = f(x)
Math.abs(Math.abs(-5)) === Math.abs(-5)    // 5 и 5: идемпотентна
addOne(addOne(5)) === addOne(5)            // 7 и 6: нет
Math.sqrt(Math.sqrt(16)) === Math.sqrt(16) // 2 и 4: нет

// операции: повтор того же вызова
obj.city = 'Astana'; obj.city = 'Astana';  // состояние то же: идемпотентно
set.add(1);          set.add(1);           // в Set один элемент: идемпотентно
arr.push(1);         arr.push(1);          // два элемента: нет
```

В вебе слово используют во втором смысле: тот же запрос повторили, а состояние сервера такое же, как после первого раза. **Ответ при этом может быть другим.** Повторный `DELETE /users/42` вернёт 404 вместо 204, но пользователя нет в обоих случаях. Зачем это нужно: клиент, у которого потерялся ответ, не знает, дошёл ли запрос. Идемпотентный запрос он может просто повторить.

## Как чистота и идемпотентность соотносятся

Чистота и идемпотентность в смысле `f(f(x)) = f(x)` не зависят друг от друга, поэтому заполнены все четыре клетки:

| | Идемпотентна | Не идемпотентна |
|---|---|---|
| **Чистая** | `abs`, `trim` | `addOne` |
| **Нечистая** | `setCity(user)` (ставит `user.city = 'Astana'`) | `arr.push(1)` |

```js
const addOne = (x) => x + 1;                       // чистая, не идемпотентная
const setCity = (user) => { user.city = 'Astana'; }; // нечистая (мутирует), но повтор ничего не добавляет
```

По каждому свойству («—» означает, что вопрос к функции не применим):

| Функция | Детерминирована | Без побочных эффектов | Идемпотентна |
|---|---|---|---|
| `abs(x)` | да | да | да |
| `addOne(x)` | да | да | нет |
| `Date.now()` | нет | да | — (аргументов нет, применить к результату нельзя) |
| `setCity(user)` | — (ничего не возвращает) | нет | да (в смысле операции) |
| `arr.push(1)` | нет (возвращает новую длину) | нет | нет |

У чистой функции нет побочных эффектов, поэтому её повтор состояние не меняет и вызывать её повторно безопасно. Но идемпотентной в смысле `f(f(x)) = f(x)` она при этом быть не обязана (`addOne`).

## HTTP-методы

| Метод | Safe | Идемпотентен | Cacheable |
|---|---|---|---|
| `GET` | да | да | да |
| `HEAD` | да | да | да |
| `OPTIONS` | да | да | нет |
| `PUT` | нет | да | нет |
| `DELETE` | нет | да | нет |
| `POST` | нет | нет | на практике нет |
| `PATCH` | нет | не гарантирован, зависит от тела | нет |

### Safe
Safe-метод по своему назначению ничего не меняет на сервере. Клиент вызывает его, не отвечая за последствия, поэтому браузер, префетч, краулеры и кеши вправе вызывать его сами.

Safe — это вопрос про побочные эффекты, но только для запросов и только в отношении состояния сервера. Поэтому safe мягче чистоты:

| Свойство | Что запрещает | `GET /users` |
|---|---|---|
| Чистота | Писать наружу и читать изменяемое снаружи | не чистый: ответ зависит от данных на сервере |
| Safe | Только менять состояние сервера | safe |
| Идемпотентность | Накапливать эффект при повторе | идемпотентен |

**Safe строже идемпотентности.** Любой safe-метод идемпотентен: если запрос ничего не меняет, повтор тоже ничего не изменит. Обратное неверно: `PUT` и `DELETE` идемпотентны, но они по назначению меняют состояние, поэтому не safe.

**Что safe разрешает.** Побочные эффекты, которые клиент не просил и за которые не отвечает: запись в лог, счётчик просмотров, обновление кеша. Запрещены только изменения, ради которых клиент пришёл.

**Safe — это контракт, а не гарантия.** Написать `GET /delete?id=5` можно, и он будет работать. Но префетч, краулер или антивирус, который проверяет ссылки в почте, перейдут по такой ссылке сами и удалят данные. Поэтому подтверждение или отписку по ссылке из письма делают страницей с кнопкой, а само действие выполняют через POST.

### Почему PUT идемпотентен, а POST нет
- `PUT /users/42 {name: "Ann", city: "Astana"}` означает «пусть ресурс 42 будет **таким**». Клиент сам задаёт итоговое состояние, поэтому после второго раза оно то же, что после первого.
- `POST /orders {item: 7}` означает «обработай / создай новый». Сервер каждый раз создаёт новый заказ с новым id, и два вызова дают два заказа.

Идемпотентность обеспечивает **реализация сервера**, а не название метода. Если `PUT` внутри прибавляет счётчик, контракт нарушен.

### PATCH зависит от тела
PATCH — частичное изменение. По спецификации он не safe и не обязательно идемпотентен. Всё решает тело:

```http
PATCH /users/42   {"city": "Astana"}                          // задаёт значение: идемпотентно
PATCH /users/42   {"op": "add", "path": "/tags/-", "value": "x"} // добавляет в массив: нет
PATCH /accounts/1 {"balance": {"increment": 100}}             // прибавляет: нет
```

Если не знаешь, как PATCH реализован на сервере, считай его неидемпотентным.

### Cacheable
Ответ можно сохранить и потом отдать снова, не обращаясь к серверу. На практике кешируют `GET` и `HEAD`. Ответ на `POST` спецификация разрешает кешировать только при явных заголовках свежести, и кеши этим почти не пользуются.

### Idempotency-Key
Это способ безопасно повторять неидемпотентный `POST`. Если API его не поддерживает, не поможет.

```http
POST /payments
Idempotency-Key: 9f1c2e7a-...   // UUID, один на логическую операцию
```

- Клиент генерирует ключ **один раз на операцию** и при ретраях отправляет тот же ключ.
- Сервер запоминает пару «ключ → результат». Если ключ пришёл повторно, сервер не выполняет операцию заново, а возвращает сохранённый результат.
- Для новой операции нужен новый ключ, иначе сервер вернёт результат старой.

### Что из этого следует на практике
- Ретраить можно `GET`, `PUT`, `DELETE`. `POST` — только с `Idempotency-Key`.
- `GET /search` safe и идемпотентен по контракту HTTP, но функция, которая его вызывает, нечистая: ответ зависит от данных на сервере.
- Функция-обёртка над `PUT /users/42` идемпотентна по серверу. Но если она ещё и пишет в локальное состояние (`results.push(...)`), смотреть надо на **всё**, что она меняет, а не только на запрос.

## Частые ошибки понимания
- **Детерминированность ≠ идемпотентность.** Детерминированность — про одинаковый результат при одинаковых аргументах, идемпотентность — про повтор. `addOne` детерминирована, но не идемпотентна. `setCity(user)` идемпотентна, но про её детерминированность спрашивать бессмысленно: она ничего не возвращает.
- **Идемпотентность ≠ одинаковый ответ.** Важно итоговое состояние: второй `DELETE` возвращает 404, а не 204, но состояние то же.
- **Чистая ≠ идемпотентная.** `addOne` чистая, но `addOne(addOne(5)) !== addOne(5)`.
- **Safe — свойство запросов, а не функций.** У функции спрашивают про чистоту и побочные эффекты. Слова «safe-функция» в этом смысле нет.
- **`PUT` и `DELETE` не safe**, хотя идемпотентны: по назначению они меняют состояние.
- **Safe ≠ чистый.** `GET` читает изменяемые данные сервера, поэтому не чистый, но он safe.
- **Метод сам ничего не гарантирует.** Safe и идемпотентность — обещание сервера. `GET`, который удаляет, или `PUT`, который прибавляет, нарушают контракт.

## Вопросы для самопроверки

> [!question]- Чем детерминированность отличается от идемпотентности?
> Детерминированность сравнивает два независимых вызова с одинаковыми аргументами и смотрит на результат. Идемпотентность сравнивает один вызов с повторными и смотрит на итоговое значение или состояние.

> [!question]- Чистая ли `x => x * (1 + TAX)`, если `const TAX = 0.12`? А если `const config = { tax }` и читается `config.tax`?
> В первом случае чистая: примитив в `const` не меняется. Во втором нечистая: `const` защищает только привязку, а поле объекта можно изменить.

> [!question]- Почему функция с `fetch('/users')` (GET) нечистая, хотя GET safe?
> Ответ зависит от внешнего мира, так что функция не детерминирована, а сам запрос — это ввод-вывод. Safe говорит лишь о том, что сервер не меняется. Для чистоты этого недостаточно.

> [!question]- Приведи пример для каждой клетки «чистая/нечистая × идемпотентная/нет».
> Чистая и идемпотентная: `abs`. Чистая, не идемпотентная: `addOne`. Нечистая, идемпотентная: `setCity(user)`. Нечистая, не идемпотентная: `arr.push(1)`.

> [!question]- Идемпотентен ли `sqrt` в смысле `f(f(x)) = f(x)`?
> Нет: `sqrt(sqrt(16)) = 2`, а `sqrt(16) = 4`.

> [!question]- Первый `DELETE /users/42` вернул 204, второй 404. Нарушена ли идемпотентность?
> Нет. Идемпотентность касается состояния, а не ответа: после обоих запросов пользователя 42 нет.

> [!question]- Почему PUT идемпотентен, а POST нет?
> PUT задаёт итоговое состояние ресурса целиком, и повтор приводит к тому же состоянию. POST каждый раз создаёт новое или выполняет действие заново.

> [!question]- Когда PATCH идемпотентен?
> Когда тело задаёт значения (`{"city": "Astana"}`). Если тело что-то добавляет или прибавляет (append в массив, increment), PATCH не идемпотентен.

> [!question]- Почему PUT и DELETE идемпотентны, но не safe? И почему любой safe-метод идемпотентен?
> PUT и DELETE по назначению меняют состояние сервера. Safe-метод его не меняет вовсе, так что повтор ничего не может накопить.

> [!question]- Почему отписку по ссылке из письма нельзя делать через `GET /unsubscribe?id=…`?
> Safe — это контракт: префетч, краулеры и почтовые сканеры сами переходят по GET-ссылкам и отпишут пользователя без его участия. Ссылка должна вести на страницу с кнопкой, а действие выполняется через POST.

> [!question]- Как безопасно повторить POST-оплату после таймаута?
> Отправить тот же запрос с тем же `Idempotency-Key`, если API его поддерживает. Сервер вернёт сохранённый результат и не спишет деньги второй раз.

> [!question]- Что можно делать в safe-запросе, не нарушая контракт?
> Побочные эффекты, о которых клиент не просил: логирование, счётчик просмотров, прогрев кеша.

## Связи
- [[Closures]] — функция, которая через замыкание читает изменяемую внешнюю переменную (`let tax`), нечистая. По той же причине stale closure видит старое значение.
- [[RTK Query]] — `query` соответствует safe и cacheable чтению, у которого есть кеш и дедупликация. `mutation` — не safe, после неё кеш нужно инвалидировать. Повторять мутацию можно, только если она идемпотентна.
