# HTTPS и TLS

**Определение.** HTTPS — это HTTP поверх TLS (Transport Layer Security). TLS защищает соединение тремя способами: шифрует данные, проверяет их целостность и подтверждает, что ты говоришь с настоящим сервером. SSL (Secure Sockets Layer) — устаревший предшественник TLS, имя осталось в разговорной речи («SSL-сертификат»).

## Целостность и аутентификация — разные защиты
Это две разные атаки, и одна защита не заменяет другую.

| | Подмена данных | Подмена сервера (MITM, «человек посередине») |
|---|---|---|
| Что делает атакующий | Меняет байты по дороге, ключа у него нет | Притворяется сервером и сам вырабатывает ключ с тобой |
| С кем ты говоришь | С настоящим сервером | Не с тем сервером |
| Что ловит | Целостность: тег не сойдётся | Аутентификация: сертификат не пройдёт проверку |

### Как работает целостность
1. **Общий ключ появляется в handshake.** Стороны обмениваются промежуточными значениями (обмен Диффи-Хеллмана, в TLS обычно ECDHE, Elliptic Curve Diffie-Hellman Ephemeral — на эллиптических кривых с временными значениями), и каждая вычисляет у себя один и тот же ключ. Сам ключ по сети не идёт, и по перехваченным значениям его не вычислить.
2. **Отправитель считает тег** (MAC, Message Authentication Code — короткий проверочный код) от данных записи (блок до 16 КБ), её порядкового номера и ключа. Тег короткий, у современных шифров 16 байт. По сети уходят данные и тег, ключа там нет. Шифры AEAD (Authenticated Encryption with Associated Data) шифруют и считают тег за один проход.
3. **Получатель** считает тег сам и сравнивает с пришедшим. Не совпало — соединение обрывается.

Пример: ушло «перевод 100» с тегом `a7f3`. Атакующий меняет текст на «перевод 900», тег оставляет. Получатель считает тег от «перевод 900», получает `5c1e` и обрывает соединение. Подобрать верный тег без ключа нельзя.

Номер записи входит в расчёт, поэтому записи нельзя переставить, выбросить или повторить. Большой ответ идёт сотнями записей, и у каждой свой тег.

**Почему целостности мало.** Посредник вырабатывает ключ с тобой сам и ставит правильные теги. Целостность защищает от тех, у кого нет ключа, но не от того, с кем ты ключ выработал.

### Как работает аутентификация
Держится на двух вещах вместе:
- **сертификат**: «публичный ключ K принадлежит `bank.com`», подписанный центром сертификации, которому доверяет браузер;
- **подпись handshake**: сервер подписывает данные handshake своим **приватным** ключом, браузер проверяет её публичным ключом из сертификата.

Сертификат публичный, скопировать его может кто угодно. Но подписать handshake можно только приватным ключом, а он есть только у настоящего сервера.

При подмене:
- подделать подпись без приватного ключа банка нельзя;
- сертификат на `bank.com` центр атакующему не выдаст: сначала проверяет контроль над доменом;
- свой сертификат на другое имя показать можно, но браузер сверит имя и покажет красную страницу, curl и Node упадут с ошибкой;
- `NODE_TLS_REJECT_UNAUTHORIZED=0` и `curl -k` отключают именно эту проверку: канал зашифрован, но с кем ты говоришь, неизвестно.

**Чего TLS по умолчанию не проверяет**: кто клиент. Для этого нужен логин или токен, либо mTLS (mutual TLS), где сертификат предъявляют обе стороны.

## Сертификат

| Поле | Что значит |
|---|---|
| Домены (SAN, Subject Alternative Name) | Для каких имён выдан: `example.com`, `www.example.com` |
| Публичный ключ сервера | Им проверяют подпись handshake |
| Кто выдал (issuer) | Центр сертификации |
| Срок действия | С какой даты по какую |
| Подпись центра | Подтверждает, что всё выше выдано им и не менялось |

**Проверка домена.** Браузер сверяет имя из адреса со списком SAN. Нет совпадения — `hostname mismatch` или `ERR_CERT_COMMON_NAME_INVALID`. Поэтому у атакующего может быть полностью валидный сертификат, но на `evil.com`.
- Один сертификат может покрывать несколько доменов.
- Wildcard `*.example.com` закрывает ровно один уровень (`api.example.com`, но не `a.b.example.com`) и не включает сам `example.com`.
- Старое поле CN (Common Name) браузеры не используют, смотрят только SAN.
- Контроль над доменом центр проверяет файлом на сайте (HTTP-01) или TXT-записью в DNS (DNS-01).

## Центры сертификации и цепочка доверия
**Центр сертификации (CA, Certificate Authority)** — организация, которая подтверждает, что публичный ключ принадлежит домену, и ставит подпись: Let's Encrypt, DigiCert, Sectigo, GlobalSign, Google Trust Services. Браузер не ходит к центру при каждом визите: подпись выдаётся заранее, а проверка при соединении идёт локально.

Браузер и сервер напрямую друг другу не доверяют, у них общий знакомый — центр:

| Сторона | Что есть заранее |
|---|---|
| Браузер | Список корневых сертификатов, пришедший с ОС или браузером |
| Сервер | Свой сертификат, подписанный центром после проверки домена |
| Центр | Приватный ключ, которым он подписывает |

Порядок: владелец доказывает контроль над доменом → центр подписывает сертификат → при визите браузер проверяет подпись ключом из своего списка.

**Корневой сертификат** — файл с публичным ключом центра. Он самоподписанный: доверие к нему берётся не из подписи, а из того, что он лежит в хранилище. Это единственное место, где доверие принимается без проверки.

| Где | Чей список |
|---|---|
| Windows | Microsoft |
| macOS, iOS | Apple |
| Android | Google |
| Chrome | Chrome Root Store (Google) |
| Firefox | Mozilla |
| Linux | Пакет `ca-certificates` на основе списка Mozilla |
| Node.js | Встроенный список Mozilla |

В списки попадают центры, прошедшие аудит, это порядка одной-двух сотен корней. Нарушителя убирают обновлением: DigiNotar после взлома в 2011, Symantec в 2018. Посмотреть список: `certmgr.msc` на Windows, «Связка ключей» на macOS.

**Промежуточные центры.** Ключ корня хранят офлайн и почти не трогают. Сертификаты сайтам каждый день выдают промежуточные центры, которые корень один раз подписал. Цепочка: сайт → промежуточный → корневой. Взломали промежуточный — его отзывают, корень цел. Если цепочка не дошла до корня из хранилища: `unable to get local issuer certificate`, обычно сервер не отдал промежуточный сертификат.

### Следствия
- Node берёт встроенный список Mozilla, а curl и браузеры — хранилище ОС. Отсюда «в браузере работает, в Node нет».
- mkcert кладёт свой корень в хранилище, чтобы браузер доверял локальным сертификатам.
- Корпоративные прокси, расшифровывающие HTTPS, ставят сотрудникам свой корень.
- **Чужой корень в хранилище** — браузер поверит любому сертификату от его имени. По сети его не положить, только на самой машине: так делают mkcert, корпоративные прокси и вредоносное ПО. Не ставь чужие корни.
- Клиентские сертификаты для mTLS выдаёт тот, кто их требует (компания, банк), и ставит на устройство вручную или через MDM. В обычном вебе их нет.

## Частые ошибки понимания
- **«Шифрование значит, что сервер настоящий».** Шифрование и целостность работают и с посредником. Сервер подтверждает только сертификат с подписью handshake.
- **«`curl -k` просто убирает предупреждение».** Он убирает всю аутентификацию сервера.
- **«TLS знает, кто клиент».** Нет, только mTLS. Обычно клиента определяет логин или токен.
- **«Wildcard покрывает всё».** Один уровень, и без голого домена.
- **«При каждом визите браузер спрашивает центр».** Проверка подписи идёт локально по корням из хранилища.

## Связи
- [[HSTS]] — TLS защищает соединение, но первый запрос по `http://` уходит открытым. HSTS заставляет браузер сразу идти по HTTPS.
- [[Отладка веб-запросов]] — `unable to get local issuer certificate`, mixed content, «в браузере работает, в Node нет».
- [[CDN]] — CDN снимает TLS на своих узлах и держит сертификат домена.
- [[Сессии и JWT]] — подпись JWT устроена по тому же принципу: проверка публичным ключом, подделка без приватного невозможна.
- [[HTTPS за прокси]] — TLS часто снимает прокси, и приложение видит HTTP. Forward proxy и `CONNECT`.
