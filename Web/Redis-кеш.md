# Redis-кеш

**Определение.** Redis — отдельный сервер, который хранит пары «ключ → значение» в оперативной памяти и поэтому отвечает за доли миллисекунды. **Это не HTTP-кеш**: `Cache-Control`, `private` и `Vary` он не читает и ничего по ним не решает. Что кешировать, под каким ключом и на какой срок, пишешь в коде ты сам. Кеш общий для всех запросов приложения.

## Шаблон cache-aside

```js
async function getUser(id) {
  const key = `user:${id}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);          // cache hit
  const user = await db.getUser(id);              // cache miss
  await redis.set(key, JSON.stringify(user), 'EX', 60);
  return user;
}
```

**Что Redis делает сам:**
- TTL: удаляет ключ, когда истекает `EX`;
- вытесняет ключи при нехватке памяти. Нужны `maxmemory` и политика вытеснения, для кеша обычно `allkeys-lru`. Без политики запись упрётся в ошибку;
- поддерживает типы данных: строки, хеши, списки, счётчики `INCR`.

## Ключ
Ключ — имя (строка), под которым значение лежит в Redis. Redis устроен как словарь: по ключу кладёшь значение и по тому же ключу достаёшь (`redis.set('profile:42', ...)`, `redis.get('profile:42')`). Одинаковый ключ означает одну и ту же ячейку.

Поэтому в ключ включают **всё, от чего зависит результат**: пользователя, язык, права, параметры запроса. Ключ `profile` без id для всех пользователей указывает на одну ячейку, и один пользователь получит данные другого. `profile:42` их разделяет.

Так же устроен кеш в памяти процесса. Разница в том, что он общий только для запросов одного инстанса, и у каждого инстанса свой.

## Инвалидация
Это главная сложность кеширования.

| Подход | Минус |
|---|---|
| Только TTL | Данные устаревшие до истечения срока |
| Удалить ключ после записи в БД (`redis.del`) | Удалять нужно в каждом месте, где данные меняются. Первое чтение после записи идёт в БД |
| Записать новое значение в Redis сразу после записи в БД | Значение нужно собрать в том же виде, что при чтении. При сбое между шагами или двух одновременных записях в кеше может остаться старое значение |

Разница между подходами — в том, что лежит в кеше сразу после записи:

```js
// удалить ключ: кеш пуст, следующее чтение заполнит его заново (cache-aside)
await db.users.update(id, data);
await redis.del(`user:${id}`);

// обновить значение: в кеше сразу новое
await db.users.update(id, data);
await redis.set(`user:${id}`, JSON.stringify(newUser), 'EX', 60);
```

**Удаление проще и надёжнее.** Причин две.
1. Код записи не собирает значение для кеша, а только удаляет ключ по имени. Логика сборки остаётся в одном месте — в коде чтения.
2. Порядок одновременных записей не важен. Вот гонка при обновлении: для одного пользователя одновременно идут запись A (`city = Almaty`) и запись B (`city = Astana`).

```
t1  A: UPDATE в БД (Almaty)
t2  B: UPDATE в БД (Astana)      ← последним в БД записан B, актуально Astana
t3  B: redis.set → Astana
t4  A: redis.set → Almaty        ← запрос A затянулся (сеть, пауза процесса) и дошёл до Redis позже
итог: в БД Astana, в Redis Almaty до конца TTL
```

БД и Redis — два разных сервера, общей транзакции между ними нет, и два шага одного запроса (запись в БД, запись в Redis) не атомарны. A и B могут быть двумя вызовами одной функции (два пользователя, двойной клик, повтор после таймаута), разными местами кода (админка, импорт, фоновая задача) или разными серверами приложения. Шаги разных запросов перемешиваются, поэтому порядок записей в БД и в Redis не обязан совпадать. При удалении оба запроса просто убирают ключ, и следующее чтение возьмёт актуальное значение из БД.

**Цена удаления:** первое чтение после каждой записи идёт в БД.

**На практике** используют TTL плюс удаление ключа при изменении.

## Подводные камни
- **Cache stampede.** Популярный ключ протух, и сотня запросов одновременно идёт в БД. Лечат блокировкой на пересчёт и разбросом TTL.
- **Redis недоступен.** Приложение должно продолжать работать без кеша.
- **Сериализация.** После `JSON.stringify` даты превращаются в строки.

## Два слоя кеша
Путь ответа: `Браузер → CDN → бэкенд → Redis → БД`. Redis работает до отправки ответа, HTTP-кеши — после. Обновлять данные нужно с учётом обоих слоёв: сбросил Redis, а старый ответ ещё лежит в CDN или в браузере.

**Три срока не путать:**
- TTL ключа в Redis — сколько значение живёт до автоудаления;
- `max-age` — сколько браузер или CDN считает копию свежей;
- TTL подписанной ссылки — сколько ссылка даёт доступ.

## Частые ошибки понимания
- **«Redis уважает `Cache-Control`».** Нет, он про HTTP ничего не знает.
- **Ключ без id пользователя для персональных данных.** Один пользователь получит данные другого.
- **«Запишу новое значение — так свежее».** При гонке в кеше может остаться старое. Удаление надёжнее.
- **«Сбросил Redis — пользователи видят новое».** Старый ответ может ещё лежать в CDN или браузере.
