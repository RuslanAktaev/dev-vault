# OAuth 2.0

**Определение.** OAuth 2.0 — протокол **авторизации**. Пользователь логинится у провайдера (Google, GitHub), а приложение получает токен с ограниченными правами и пароль пользователя не видит никогда. Для браузерных и мобильных приложений достаточно знать один flow: **Authorization Code + PKCE**.

## OAuth и OIDC
- **OAuth 2.0** отвечает на вопрос «что приложению разрешено»: «разрешаю приложению читать мои календари».
- **OpenID Connect (OIDC)** — надстройка над OAuth для **аутентификации**: «это именно пользователь X». «Войти через Google» — это OIDC. Подробно в [[OIDC]].

## Роли

| Роль | Кто это |
|---|---|
| Resource Owner | Пользователь |
| Client | Твоё приложение |
| Authorization Server | Провайдер: логинит пользователя и выдаёт токены |
| Resource Server | API с данными |

## Регистрация Client
Перед первым входом Client один раз регистрируют у Authorization Server, в консоли провайдера (Google, GitHub, Keycloak и т. д.). При регистрации указывают:
- **тип приложения** (web, SPA, native). От него зависит, будет ли у Client секрет;
- **`redirect_uri`** — точные адреса, на которые провайдер вернёт пользователя. При входе значение должно совпасть посимвольно. Для dev и prod адреса разные;
- **scopes** — минимально необходимые.

Провайдер выдаёт `client_id` (публичный идентификатор), а серверным приложениям ещё и `client_secret`. У SPA и мобильных приложений секрета нет, вместо него используется [[PKCE]]. Секрет часто показывают только один раз: потерял — выпускаешь новый.

### Что где хранить

| Что | Секретно? | Где хранить |
|---|---|---|
| `client_id` | нет | Конфиг или env. В браузере он и так виден в URL `/authorize` |
| `client_secret` | да | Только на бэкенде: env или менеджер секретов. Не в git, не в клиентском бандле (в Next.js не в `NEXT_PUBLIC_*`), не в логах |
| `redirect_uri` | нет | Конфиг. Должен совпадать с зарегистрированным |
| `access_token` | да | Короткоживущий: серверная сессия или память. Не в логах и не в URL |
| `refresh_token` | да, долгоживущий | Только на бэкенде, в БД (лучше зашифрованным). В браузер не отдают |
| `code_verifier`, `state`, `nonce` | временные | На время входа: серверная сессия (бэкенд) или `sessionStorage` (SPA) |

**Правила обращения с секретами.**
- Для dev и prod отдельные `client_id` и `client_secret`.
- `.env` в `.gitignore`. В CI и на хостинге секреты задают через их хранилище секретов.
- Если секрет утёк, его отзывают и выпускают новый, старый сразу перестаёт работать.
- Если токены нужны SPA, их держит бэкенд (BFF), а браузер получает только куку сессии.

**Если провайдер ты сам:**
- `client_secret` хранят только в виде хеша, как пароль, и показывают один раз при создании;
- `redirect_uri` каждого клиента сверяют с сохранённым списком;
- `code` делают одноразовым и короткоживущим.

## Authorization Code + PKCE по шагам
1. **Client** генерирует `code_verifier` (секрет, остаётся у Client) и считает от него хеш `code_challenge`. Затем перенаправляет **Resource Owner** на `/authorize` **Authorization Server**, передав `client_id`, `redirect_uri`, `scope`, `state` и `code_challenge`. Сам `code_verifier` не передаётся.
2. **Resource Owner** логинится у **Authorization Server** и даёт согласие. Authorization Server запоминает `code_challenge` вместе с этим входом.
3. **Authorization Server** перенаправляет **Resource Owner** обратно на `redirect_uri` с одноразовым `code`.
4. **Client** отправляет на `/token` прямой запрос с `code` и `code_verifier`. Authorization Server хеширует `code_verifier`, сверяет с запомненным `code_challenge` и при совпадении выдаёт токены: `access_token`, `refresh_token`, а в OIDC ещё `id_token`.
5. **Client** ходит с `access_token` к **Resource Server** за данными.

Зачем так сложно: токены не проходят через адресную строку, а перехваченный `code` без `code_verifier` бесполезен. Механика PKCE подробно в [[PKCE]].

**Confidential client** — Client с бэкендом и `client_secret`. Ему PKCE не обязателен: на шаге 1 он не генерирует verifier и challenge, а на шаге 4 отправляет `code` вместе с `client_id` и `client_secret`. Тем не менее PKCE рекомендуется всем, а в OAuth 2.1 обязателен.

## Flows

| Flow | Когда |
|---|---|
| Authorization Code + PKCE | Веб, SPA, мобильные приложения |
| Client Credentials | Сервис к сервису, без пользователя |
| Device Code | ТВ и CLI |
| Refresh Token | Обновление access-токена |

Implicit и Resource Owner Password Credentials (ROPC) устарели, их не используют.

## OAuth 2.1
OAuth 2.1 — не новый протокол, а сводка OAuth 2.0 с уже принятыми рекомендациями по безопасности в одной спецификации. В источнике разобран черновик IETF draft-ietf-oauth-v2-1-15, окончательного RFC на тот момент не было. Актуальный статус — на datatracker.ietf.org.

| Что | OAuth 2.0 | OAuth 2.1 |
|---|---|---|
| PKCE | Расширение, для public clients рекомендуется | Обязателен для Authorization Code |
| Implicit (`response_type=token`) | Есть | Убран: токен в адресной строке утекает и не привязан к отправителю |
| Resource Owner Password Credentials | Есть | Убран |
| `redirect_uri` | Допускалось сравнение по шаблону | Только точное посимвольное совпадение |
| Bearer-токен в query string | Допускался | Убран: только заголовок `Authorization` или тело запроса |
| Refresh token у public clients | Без ограничений | Привязан к отправителю (sender-constrained) или одноразовый (ротация) |
| `redirect_uri` в запросе на `/token` | Передавался | Больше не передаётся |

Остаются Authorization Code (всегда с PKCE), Client Credentials и Refresh Token.

**Для нового проекта:** Authorization Code + PKCE, точные `redirect_uri`, токены только в заголовке, ротация refresh-токенов. Implicit и Password не использовать.

## Где применяется
«Войти через…», доступ к API провайдера от имени пользователя (календарь, репозитории), сервис-к-сервису (Client Credentials). На практике авторизацию берут готовой: Auth.js, Auth0, Clerk, Keycloak, Supabase Auth. Понимать flow нужно, чтобы её настраивать и отлаживать, а не чтобы писать с нуля.

## Мелочи, которые ломают интеграцию
- **`state`** — случайная строка, которую сверяют при возврате. Защищает сам редирект-поток от CSRF.
- **`redirect_uri`** должен совпадать с зарегистрированным символ в символ. Иначе ошибка `redirect_uri mismatch`.
- В OIDC добавляется **`nonce`**: защита от повторного использования `id_token`.
- `scope` запрашивают минимальные.
- Код на токены лучше обменивать на бэкенде, где можно хранить `client_secret`. SPA без бэкенда использует PKCE без секрета.

## Частые ошибки понимания
- **«OAuth — это логин».** OAuth — про права доступа. Кто вошёл, говорит OIDC.
- **«`code` — это токен».** Это одноразовая квитанция для обмена на токены, сама она ничего не открывает.
- **`client_secret` в SPA или в `NEXT_PUBLIC_*`.** Всё, что попало в бандл, публично.
- **Отдавать `refresh_token` в браузер.** Он долгоживущий, его место на бэкенде.
- **Путать `state`, `nonce` и PKCE.** `state` защищает редирект от CSRF, `nonce` — `id_token` от повтора, PKCE — обмен `code` на токены.
