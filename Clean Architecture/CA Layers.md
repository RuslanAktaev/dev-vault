# CA Layers

Концентрические круги Clean Architecture. Суть не в количестве слоёв, а в **Dependency Rule**.

## Dependency Rule
**Зависимости исходного кода направлены только внутрь** — к более высокоуровневой политике. Внутренний круг ничего не знает о внешнем: ни имён, ни функций, ни форматов данных.

## Слои (изнутри наружу)
1. **Entities** — критические бизнес-правила предприятия. Существовали бы и без программы (расчёт процента по кредиту). Меняются реже всего.
2. **Use Cases** — бизнес-правила конкретного приложения. Оркестрируют Entities. Общаются с внешним миром через **Input/Output Ports** (интерфейсы, объявленные на стороне use case).
3. **Interface Adapters** — конвертация данных между форматом use case и форматом внешних систем: Controllers, Presenters, ViewModels, Gateways/Repositories-реализации. Здесь знают про SQL, HTTP, UI-модели.
4. **Frameworks & Drivers** — БД, веб-фреймворк, UI-фреймворк, внешние API. «Детали», минимум кода, только склейка.

## Пересечение границ
- Поток управления: Controller → Use Case → Presenter. Зависимость Use Case → Presenter развёрнута через Output Port (DIP).
- Через границы идут **простые структуры данных** (DTO), а не Entities и не строки из ORM/БД.

## Во фронтенде
Аналог: domain (модели и правила) → application (сценарии, хуки-оркестраторы) → adapters (API-клиенты, мапперы) → UI/фреймворк. React и Redux — детали, а не центр.

## Частые ошибки понимания
- «Нужно ровно 4 круга». Нет: кругов может быть больше или меньше, важно правило зависимостей.
- Entities = модели ORM. Нет: ORM-модели — деталь внешнего слоя.
- Use case = эндпоинт или CRUD. Use case — это сценарий приложения, а не транспорт.
- Архитектура «кричит» о фреймворке (screaming architecture нарушена): структура должна показывать предметную область.

## Связи

- [[Boundaries]] — каждый переход между кругами — архитектурная граница.
