# Boundaries

Архитектура — это искусство проводить **границы**, отделяющие важное (бизнес-правила) от деталей (БД, UI, фреймворки). Граница — место, где зависимость пересекает линию **в сторону высокого уровня**.

## Decoupling modes
Одна и та же логическая граница может быть реализована по-разному:
- **Source level** — монолит, разделение модулями и интерфейсами. Самое дешёвое.
- **Deployment level** — отдельно деплоимые единицы (jar, dll, npm-пакет), но в одном процессе.
- **Service level** — отдельные процессы или сервисы, общение по сети. Самое дорогое.

Хорошая архитектура позволяет **переходить** между режимами по мере необходимости и откладывать решение.

## Humble Object
Разделить поведение на трудно тестируемое и тестируемое:
- **Humble** — максимально тупая часть у границы (View, SQL-запрос, вызов внешнего API).
- Тестируемая часть — вся логика (Presenter готовит ViewModel со строками и флагами, View просто рисует).
- Во фронтенде: презентационный компонент + хук или селектор, который готовит данные.

## Partial boundaries
Полная граница дорогая (интерфейсы в обе стороны, отдельные компоненты). Упрощённые варианты:
- **Skip the last step** — все интерфейсы есть, но всё в одном компоненте.
- **One-dimensional boundary** — Strategy: интерфейс только в одну сторону.
- **Facade** — даже без инверсии зависимостей, только точка входа.

Цена: такие границы со временем деградируют. Решение — баланс YAGNI и стоимости добавить границу позже.

## HAL / OSAL / PAL (Clean Embedded Architecture)
Слои, которые отделяют софт от железа, чтобы бизнес-логику можно было тестировать **off-target** (без целевого железа):
- **HAL** — Hardware Abstraction Layer: железо (порты, регистры) за интерфейсом в терминах приложения.
- **OSAL** — OS Abstraction Layer: изоляция от RTOS или ОС.
- **PAL** — Processor Abstraction Layer: изоляция от конкретного процессора и компилятора.
Мысль: «firmware» — код, завязанный на железо. Хотим, чтобы его было как можно меньше.

## Частые ошибки понимания
- Граница = сетевой вызов. Нет: граница — это направление зависимостей, режим развязки вторичен.
- `main` — тоже граница: самый «грязный» плагин, который собирает всё вместе.
- Тесты — тоже компонент системы и тоже должны быть отделены границей (Testing API), иначе они хрупкие.
