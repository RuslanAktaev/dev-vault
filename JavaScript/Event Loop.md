# Event Loop

**Определение.** JS выполняет код в **одном потоке** на одном call stack. Асинхронность обеспечивает окружение (браузер или Node): оно выполняет операции и ставит колбэки в очереди. Event Loop берёт их по одной, **когда стек пуст**.

Таймеры, `fetch` и DOM — не часть языка, их даёт среда (Web API в браузере, libuv в Node). Работу делает среда, а в очередь попадает колбэк, когда она готова.

## Модель (браузер)
1. Выполнить одну **задачу** (macrotask): сам скрипт тоже задача, `setTimeout`, `setInterval`, событие, сетевой колбэк, `MessageChannel`.
2. Выполнить **все микрозадачи** до опустошения очереди: реакции промисов (`then` / `catch` / `finally`, продолжение после `await`), `queueMicrotask`, `MutationObserver`. Микрозадачи, созданные в процессе, тоже выполняются.
3. Если пора, **рендер**: `requestAnimationFrame` → style → layout → paint.
4. Повторить.

```js
console.log(1);
setTimeout(() => console.log(4));
Promise.resolve().then(() => console.log(3));
console.log(2);
// 1 2 3 4
```

## Промисы и `async` синхронны до первой паузы
- `new Promise(executor)` выполняет `executor` **синхронно**. В очередь микрозадач уходит только реакция (`then`).
- `async`-функция выполняется синхронно до первого `await`. Всё после `await` идёт микрозадачей.
- `async`-функция всегда возвращает промис. `throw` внутри превращается в rejected-промис, поэтому `try/catch` вокруг вызова без `await` ошибку не поймает.

```js
async function f() {
  console.log('A');   // синхронно
  await null;
  console.log('C');   // микрозадача
}
f(); console.log('B'); // A B C

try { fails(); } catch {}          // не поймает: fails() вернула rejected-промис
try { await fails(); } catch {}    // поймает
```

## Node.js
Фазы: timers → pending → poll (I/O) → check (`setImmediate`) → close. `process.nextTick` выполняется **раньше** промисов между операциями.

## Где важно
- Длинная синхронная задача (>50 мс) блокирует ввод и рендер. Лечение: разбить работу, отдать управление (`setTimeout`, `scheduler.yield`), вынести в Web Worker.
- Порядок обновлений состояния после `await`, батчинг в React.
- Гонки запросов: ответы приходят в порядке завершения, а не отправки.

## Частые ошибки понимания
- `setTimeout(fn, 0)` выполнится сразу. Нет: это следующая задача, после всех микрозадач и, возможно, после рендера. Для вложенных таймеров есть минимальная задержка.
- `await` блокирует поток. Нет: он приостанавливает только функцию, остаток идёт микрозадачей.
- Бесконечная цепочка микрозадач «асинхронна, значит безопасна». Нет: она блокирует рендер так же, как синхронный цикл.
- Промисы — это «многопоточность». JS-код всё равно выполняется в одном потоке.
- «Executor промиса асинхронный». Нет: он выполняется сразу, асинхронна только реакция.
- «`try/catch` ловит ошибку `async`-функции». Только если её вызов стоит под `await`.
