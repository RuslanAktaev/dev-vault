# Виртуализированные списки

**Идея.** Виртуализированный список рендерит только окно элементов вокруг viewport с запасом, а не все N сразу.

Без виртуализации (`ScrollView` + `map`) рендерятся все элементы, и на длинных списках вроде ленты или чата интерфейс лагает. На коротких списках разницы нет.

## FlatList
Встроенное решение RN. Элемент монтируется перед появлением на экране и размонтируется, когда уходит с него.

**Минусы:**
- на тяжёлых айтемах mount и unmount обходятся дорого;
- при быстром скролле появляются белые пустоты.

**Настройки:** `keyExtractor`, `initialNumToRender`, `windowSize`, `maxToRenderPerBatch`, `removeClippedSubviews`.

**`getItemLayout`** возвращает `length`, `offset` и `index`, то есть размеры известны заранее. Он нужен для `scrollToIndex` и `initialScrollIndex` и работает только при фиксированной высоте. Обычно не нужен.

```tsx
const ITEM_HEIGHT = 72; // фиксированная высота — условие для getItemLayout

<FlatList
  data={messages}
  renderItem={renderItem}
  keyExtractor={(item) => item.id}
  // значения ниже — для примера
  initialNumToRender={10}
  windowSize={5}
  maxToRenderPerBatch={10}
  removeClippedSubviews
  getItemLayout={(_, index) => ({
    length: ITEM_HEIGHT,
    offset: ITEM_HEIGHT * index,
    index,
  })}
/>
```

## FlashList (Shopify)

### Recycling
Ячейки не размонтируются, а переиспользуются из пула. Меняется только проп `item`, поэтому это rerender, а не mount.

| | Mount / unmount | Rerender |
|---|---|---|
| Экземпляр | Создаётся / уничтожается | Тот же |
| Эффекты | Срабатывают | Эффект с `[]` не срабатывает |
| Стейт | Пропадает | Сохраняется |

Проверить, что происходит, можно через `console.log` в `useEffect(..., [])`.

```tsx
function Row({ item }: { item: Message }) {
  useEffect(() => {
    console.log('mount', item.id); // при recycling не печатается на каждый новый item
  }, []);
  return <Text>{item.text}</Text>;
}
```

### Ловушки
- **Локальный `useState` «протекает» между элементами**: переиспользованная ячейка показывает стейт предыдущего item. Лечится сбросом в `useEffect` или через `recyclingKey`.
- **Нельзя ставить `key` внутри айтема**: это ломает переиспользование.

```tsx
function Row({ item }: { item: Message }) {
  const [expanded, setExpanded] = useState(false);

  useEffect(() => {
    setExpanded(false); // сброс, когда ячейке дали другой item
  }, [item.id]);

  return (
    <Pressable onPress={() => setExpanded((v) => !v)}>
      <Text numberOfLines={expanded ? undefined : 2}>{item.text}</Text>
    </Pressable>
  );
}
```

### `getItemType`
Данные передаются в проп `data`. `getItemType(item)` возвращает стабильный ярлык типа ячейки, и пулы делятся по типам.
- Нужен для разнородных списков, для однотипных не нужен.
- Нельзя возвращать уникальное значение вроде `id`: тогда recycling не сработает.
- Вызывается до `renderItem` и работает по данным. Результат в `renderItem` не передаётся, поэтому `renderItem` проверяет тип сам.
- Сложную логику определения типа держат в одном месте: в функции или в маппинге данных с полем `type` внутри `useMemo`. Тогда в `getItemType` и `renderItem` остаётся простое чтение `item.type`.
- Без `getItemType` ничего не ломается, но при смене типа происходит обычный unmount/mount, и выигрыш пропадает.

```tsx
type Row =
  | { type: 'message'; id: string; text: string }
  | { type: 'date'; id: string; date: string };

const rows = useMemo<Row[]>(() => toRows(rawMessages), [rawMessages]); // тип считается здесь

<FlashList
  data={rows}
  getItemType={(item) => item.type} // ярлык типа, не id
  renderItem={({ item }) =>
    item.type === 'date' ? <DateSeparator date={item.date} /> : <MessageRow item={item} />
  }
/>
```

### v2 (актуальная 2.3.1)
- **Убраны:** `estimatedItemSize`, `estimatedListSize`, `estimatedFirstItemOffset`, `onBlankArea`, `disableAutoLayout`. Размеры теперь считаются динамически.
- **Добавлены:** `masonry`, `maxItemsInRecyclePool`, `onStartReached` + `onStartReachedThreshold`.

### `maintainVisibleContentPosition`
Включено по умолчанию. Нужно для чатов: при подгрузке истории список не прыгает. Параметры:
- `disabled`;
- `autoscrollToTopThreshold`, `autoscrollToBottomThreshold`;
- `animateAutoScrollToBottom`;
- `startRenderingFromBottom`.

(предположение) При сильно разной высоте элементов позиция может подёргиваться.

## Подгрузка
- `onEndReached` + `onEndReachedThreshold` — бесконечный скролл вниз. Порог задаётся долей длины видимой области.
- `onStartReached` + `onStartReachedThreshold` (FlashList v2) — подгрузка сверху, например истории чата.
- От повторных вызовов защищают флаги `isLoading` и `hasNextPage`.

```tsx
const loadMore = useCallback(() => {
  if (isLoading || !hasNextPage) return; // защита от повторных вызовов
  fetchNextPage();
}, [isLoading, hasNextPage, fetchNextPage]);

<FlashList
  data={rows}
  renderItem={renderItem}
  onEndReached={loadMore}
  onEndReachedThreshold={0.5} // доля длины видимой области, значение для примера
/>
```

## LegendList (`@legendapp/list`)
- Чистый JS поверх `ScrollView`, без нативной части.
- `recycleItems` опционален, по умолчанию `false`.
- Размеры: `estimatedItemSize` — подсказка, `getFixedItemSize` — если размеры известны точно.
- Сильные стороны — чаты и разная высота: `maintainScrollAtEnd`, `maintainVisibleContentPosition`, `alignItemsAtEnd`.

Личного опыта с LegendList у меня нет, знаю по положительным отзывам коллег.

## Общие приёмы
- Стабильный `keyExtractor`.
- Мемоизация айтемов и `renderItem`.
- Осторожность с `extraData`.
- Не создавать функции и объекты в рендере.

```tsx
const MessageRow = memo(function MessageRow({ item }: { item: Message }) {
  return <Text>{item.text}</Text>;
});

const renderItem = useCallback(
  ({ item }: { item: Message }) => <MessageRow item={item} />,
  [],
);
```

## Что когда выбирать

| Ситуация | Выбор |
|---|---|
| Короткий список | `ScrollView` + `map`, разницы нет |
| Длинный список, встроенное решение без зависимостей | FlatList |
| Тяжёлые айтемы, пустоты при быстром скролле | FlashList: recycling вместо mount/unmount |
| Разнородный список (сообщения, даты, баннеры) | FlashList + `getItemType` |
| Чат с подгрузкой истории сверху | FlashList v2: `onStartReached`, `maintainVisibleContentPosition` |
| Чат, разная высота, нужна библиотека без нативной части | LegendList (знаю по отзывам, без личного опыта) |
| Нужны `scrollToIndex` / `initialScrollIndex` при фиксированной высоте в FlatList | `getItemLayout` |

## Частые вопросы на собесе
- **Что такое виртуализация и зачем она?** Рендерится только окно вокруг viewport с запасом. `ScrollView` + `map` рендерит всё и лагает на длинных списках.
- **Чем FlashList отличается от FlatList?** FlatList монтирует и размонтирует элементы, FlashList переиспользует ячейки из пула: меняется проп `item`, это rerender, а не mount.
- **Как понять, mount это или rerender?** `console.log` в `useEffect(..., [])`: при mount печатается, при rerender нет.
- **Почему в FlashList «прыгает» стейт между строками?** Ячейка переиспользуется вместе с локальным `useState`. Сбросить в `useEffect` или через `recyclingKey`.
- **Можно ли ставить `key` внутри айтема FlashList?** Нет, это ломает переиспользование.
- **Зачем `getItemType` и что из него возвращать?** Чтобы пулы делились по типам ячеек в разнородном списке. Возвращать стабильный ярлык типа, не `id`.
- **Что будет без `getItemType` в разнородном списке?** Ничего не сломается, но при смене типа будет unmount/mount, и выигрыш пропадёт.
- **Что поменялось в FlashList v2?** Убраны `estimatedItemSize` и другие оценки размеров, размеры считаются динамически. Добавлены `masonry`, `maxItemsInRecyclePool`, `onStartReached`.
- **Когда нужен `getItemLayout`?** Для `scrollToIndex` и `initialScrollIndex` при фиксированной высоте. Обычно не нужен.
- **Как сделать подгрузку истории чата без прыжков?** `onStartReached` и `maintainVisibleContentPosition` во FlashList v2.
- **Как защититься от повторных `onEndReached`?** Флаги `isLoading` и `hasNextPage`.
- **Как оптимизировать рендер айтемов?** Стабильный `keyExtractor`, мемоизация айтемов и `renderItem`, осторожность с `extraData`, никаких новых функций и объектов в рендере.
