# New Architecture

Замена старого **Bridge** на прямое взаимодействие JS ↔ native через C++. Состав: **JSI + Fabric + TurboModules + Codegen**; рядом обычно называют Hermes — движок по умолчанию, формально отдельная часть. Включена по умолчанию с RN 0.76, поддержку библиотек сверяй с документацией своей версии.

## Что было: Bridge
- JS и native общались **асинхронными батчами JSON-сообщений** через очередь моста.
- Сериализация и копирование данных на каждый вызов, синхронные вызовы невозможны. Ошибки типов на границе — только в рантайме.
- Все нативные модули инициализировались на старте.
- Layout и измерения были асинхронными → мигания и задержки (например, при измерении view). Синхронно прочитать layout из JS было нельзя.
- Работа делилась между JS-потоком, shadow-потоком (layout) и UI-потоком, их синхронизация давала задержки и мерцание.
- Concurrent-фичи React не работали.

## Из чего состоит
| Часть | Роль | Подробно |
|---|---|---|
| JSI | C++ API: JS держит ссылки на C++-объекты и вызывает их напрямую, без сериализации, в том числе синхронно | [[JSI]] |
| TurboModules | Нативные модули на JSI: типизированный контракт, ленивая загрузка | [[TurboModules и Codegen]] |
| Codegen | По TS-спеку генерирует C++-обвязку и нативные интерфейсы, контракт проверяется на сборке | [[TurboModules и Codegen]] |
| Fabric | Рендерер: иммутабельное Shadow Tree на C++, Yoga до mount, UI-поток применяет diff. Заменил Paper | [[Fabric]] |
| Hermes | Движок по умолчанию, формально отдельная часть: AOT-байткод, реализует JSI | [[Hermes]] |

- React reconciler тот же, что и в вебе, меняется только хост.
- Fabric даёт синхронные измерения layout и concurrent-фичи React 18: `startTransition`, Suspense, автоматический батчинг.
- **Bridgeless mode** — окончательный отказ от моста.

## Коротко для собеседования
Раньше JS и натив общались через bridge: асинхронно, JSON-сообщениями. Новая архитектура строится на JSI — C++-слое, через который JS напрямую держит ссылки на нативные объекты и вызывает функции, в том числе синхронно, без сериализации. Hermes исполняет JS (байткод готовится на сборке) и реализует JSI. На JSI работают TurboModules (нативные модули с типизированным контрактом: спек на TS, Codegen генерирует обвязку, ленивая загрузка) и Fabric (React рендерит на JS, Fabric в C++ строит иммутабельное Shadow Tree, Yoga считает layout, UI-поток применяет diff). Иммутабельность даёт безопасность между потоками и concurrent-фичи.

## Вопросы на собесе
- **Что такое новая архитектура?** Замена bridge на JSI; поверх — TurboModules, Codegen, Fabric. Hermes — движок по умолчанию.
- **Чем TurboModules отличаются от старых нативных модулей?** JSI вместо JSON-моста, типизированный контракт с проверкой на сборке, ленивая загрузка, возможны синхронные вызовы.
- **Зачем Codegen?** Генерирует по TS-спеку C++-обвязку и нативные интерфейсы, чтобы контракт JS ↔ натив проверялся при сборке.
- **Что делает Hermes, чем отличается от JSC и V8?** Компилирует JS в байткод на сборке (AOT): быстрее старт, меньше памяти, но без JIT. Заменил JSC.
- **Зачем JSI, если Hermes на C++?** Движок ничего не знает о RN. JSI — интерфейс, через который C++-код RN регистрирует в движке функции и объекты и работает с JS-значениями; он же позволяет менять движок.
- **Что значит «синхронно» и не плохо ли это?** JS вызывает натив и сразу получает результат. Блокирует JS-поток, поэтому только для быстрых операций.
- **Зачем иммутабельное Shadow Tree?** Старую версию можно безопасно читать из других потоков без блокировок — основа concurrent-рендеринга и приоритизации.
- **Три фазы рендера?** Render (реконсиляция на JS-потоке, через JSI создаются ShadowNode) → commit (Yoga считает layout, дерево становится актуальным) → mount (UI-поток применяет diff к нативным view).
- **Что генерируется, а что пишется руками?** Руками — TS-спек и нативная реализация. Codegen — C++-обвязка и нативные интерфейсы. Готово в ядре — JSI и базовые классы TurboModule.
- **Где живут состояние и логика?** В JS: хуки, сторы, обработчики. Вне JS-потока — worklets Reanimated и Gesture Handler, логика нативных модулей, состояние нативных вьюх.

## Частые ошибки понимания
- «JSI делает всё синхронным». Синхронный вызов блокирует JS-поток. Тяжёлую работу по-прежнему надо делать асинхронно.
- Hermes = New Architecture. Нет: это отдельная вещь (движок). JSI просто позволяет подключать разные движки.
- «ShadowNode создаются в commit». Узлы создаются и клонируются ещё в render через JSI, commit — это layout и смена актуального дерева.
- Старые библиотеки «просто работают». Есть interop-слой, но либы без поддержки Fabric/TurboModules — частый источник проблем при миграции.

## Связи
- [[Virtual DOM]] — два хоста для одного reconciler: DOM и нативный shadow tree. Разные модели коммита.
- [[Event Loop]] — асинхронный мост работал как очередь сообщений. JSI позволяет синхронные вызовы прямо из call stack JS.
- [[Fabric]] — рендерер: хост-операции, Shadow Tree, diff, Yoga, mount, цепочка от `setState` до экрана.
- [[JSI]] — фундамент: C++ API для встраивания движка, синхронные вызовы, цепочка JS → C++ → платформа.
- [[TurboModules и Codegen]] — нативные модули и генерация обвязки по TS-спеку.
- [[Hermes]] — движок по умолчанию, реализует JSI.
