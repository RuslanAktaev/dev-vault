# SSR / SSG / ISR

Стратегии того, **когда** генерируется HTML страницы.

| Стратегия | Когда рендерится HTML | Свежесть данных | Цена |
|---|---|---|---|
| **SSG** | при сборке | на момент билда | дешёвая: CDN |
| **ISR** | при сборке + фоновая перегенерация | «почти свежие» | дешёвая + периодическая работа сервера |
| **SSR** | на каждый запрос | всегда свежие | сервер на каждый запрос, выше TTFB |
| **CSR** | в браузере | свежие | пустой HTML, хуже SEO и первая отрисовка |

## ISR подробнее
Модель **stale-while-revalidate**: по истечении `revalidate` первый запрос получает **старую** версию, а в фоне запускается перегенерация. Следующие запросы получают новую. On-demand: `revalidatePath` / `revalidateTag` (например, из вебхука CMS).

## Pages Router vs App Router
- **Pages**: явные функции — `getStaticProps` (+ `revalidate` → ISR), `getServerSideProps` (SSR), `getStaticPaths`.
- **App Router**: стратегия **выводится** из того, как ты получаешь данные. Маршрут статический по умолчанию и становится динамическим при использовании `cookies()`, `headers()`, `searchParams`, некэшируемого `fetch`. Настройки: `export const revalidate`, `dynamic`, `fetch(url, { next: { revalidate, tags } })`. Модель кэширования менялась от версии к версии (в Next 15 `fetch` по умолчанию больше не кэшируется), поэтому поведение надо сверять с версией проекта.

## Частые ошибки понимания
- SSR = «без JS на клиенте». Нет: HTML с сервера всё равно гидрируется.
- ISR даёт свежие данные сразу после `revalidate`. Нет: первый запрос после истечения получает stale.
- Случайно сделать всю страницу динамической одним вызовом `cookies()` в layout.
- Выбирать стратегию на всё приложение. Её выбирают **на маршрут** (или даже на сегмент или запрос).
